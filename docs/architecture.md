# Medallion Data Platform — Architecture

## Project Overview
A data engineering platform that ingests data from three sources into ClickHouse and transforms each through a Medallion Architecture (bronze, silver, gold). Two domains share one platform: crypto market data from Binance (batch and live) and e-commerce data from Baserow.

## Technology Stack
- Python: API extraction and ingestion logic
- Apache Airflow: Batch workflow orchestration, retries and scheduled dbt runs
- Apache NiFi: Near-real-time ingestion
- ClickHouse: Analytical database and warehouse
- dbt: SQL transformations (ELT) and data quality tests
- Docker Compose: Local service orchestration
- GitHub Actions: Continuous integration

## Data Sources
- Binance public klines API, historical (BTCUSDT, 1 minute, rolling 30 days)
- Binance public klines API, live polling every 60 seconds
- Baserow REST API (`ecommerce_demo` database: customers, products, orders)

## Architecture

```
Binance REST API (history) -> Airflow + Python -> ClickHouse bronze (crypto)
Binance REST API (live)    -> NiFi              -> ClickHouse bronze (crypto)
Baserow REST API           -> Airflow + Python -> ClickHouse bronze (raw JSON)
ClickHouse bronze -> dbt -> silver -> dbt -> gold
```

Airflow runs two daily DAGs, one per domain:

```
crypto_medallion_pipeline   (02:00 UTC): load_bronze_batch    -> dbt_run -> dbt_test
baserow_medallion_pipeline  (03:00 UTC): load_baserow_bronze  -> dbt_run -> dbt_test
```

Each DAG runs only its own dbt folder (`--select path:models/crypto` or `path:models/baserow`), so a problem in one domain never fails the other. Both use `max_active_runs=1`.

## Live Ingestion (NiFi)

```
InvokeHTTP (Binance, every 60s) -> SplitJson -> InvokeHTTP (ClickHouse)
```

- The Binance request asks for the 3 most recent candles. The last one is always still forming, so SplitJson uses `$[:-1]` to drop it.
- Each remaining candle is a single JSON array, which ClickHouse reads directly as `JSONCompactEachRow`.
- The final InvokeHTTP sends an `INSERT ... SELECT ... FROM input(...)` query. ClickHouse converts millisecond timestamps to `DateTime64`, casts price strings to floats, and tags the rows `source = 'nifi'`.
- Failure and retry relationships end in a funnel so any rejected FlowFile stays visible in a queue.
- The flow definition is exported to `nifi/flows/`.

## Crypto Domain

- Bronze: `bronze_market_candles`. Raw candles from batch and live sources, append-only, with a `source` tag and `ingested_at`. Duplicates across polls and sources are allowed here by design.
- Silver: `silver_market_candles`. Closed candles that pass sanity checks, deduplicated to one row per (symbol, interval, open_time), keeping the most recently ingested copy.
- Gold:
  - `gold_daily_price_summary`: daily OHLC, volume, trades, price change, complete-day flag.
  - `gold_hourly_market_stats`: hourly OHLC, volume, trades, complete-hour flag.
  - `gold_daily_volatility`: daily range percent, 7-day average range, volume versus 7-day average.

## Baserow Domain

- Bronze: `bronze_baserow_rows`. One generic table holding every Baserow row as raw JSON (`table_name`, `row_id`, `payload`, `extracted_at`). The loader fetches all tables before changing anything, verifies the row count against Baserow's own count, and replaces each table's rows on every run.
- Silver:
  - `silver_customers`: typed and cleaned, duplicate customers merged by email, missing countries set to `Unknown`.
  - `silver_customer_code_map`: every customer code mapped to its canonical code.
  - `silver_products`: typed, invalid prices removed.
  - `silver_orders`: typed, status spelling normalized, invalid quantities removed, customers mapped to canonical codes.
- Gold:
  - `gold_order_facts`: one row per order with customer and product attributes, gross and net amounts, and a revenue flag (Delivered and Shipped count as revenue).
  - `gold_daily_sales`: daily orders, cancellations, returns, units, revenue and average order value.
  - `gold_customer_summary`: per-customer orders, units, lifetime revenue and order dates.
  - `gold_product_performance`: per-product orders, units, revenue, return rate and average discount.

The mock data is generated by `scripts/generate_baserow_mock_data.py` and includes deliberate quality problems so the silver layer has real cleaning to do.

## Data Quality
48 dbt tests: 13 for the crypto domain and 22 for the Baserow domain, plus singular tests under `dbt/tests/`. Highlights: no duplicate candles in silver, valid price and volume values, every order references an existing customer and product, no orders lost between silver and the gold fact table, and daily revenue reconciles with per-customer revenue.

## Handling Gaps and Reruns
The live NiFi flow only collects while running. The daily crypto batch reload replaces its own `batch` rows and leaves `nifi` rows alone, and silver removes any overlap, so downtime gaps are healed without creating duplicates. The Baserow loader replaces each table's bronze rows on every run, so reruns are safe.

## CI/CD
- CI: GitHub Actions starts a temporary ClickHouse, creates the bronze tables from `clickhouse/init/`, loads synthetic crypto candles and synthetic Baserow rows (both deliberately messy), then runs `dbt run` and `dbt test` on every push and pull request.
- CD: Not implemented. The stack runs locally, so there is no deployment target. With one, a deploy job would run after CI passes on `main`.
